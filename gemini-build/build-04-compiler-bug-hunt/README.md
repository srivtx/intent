# Build 04: 7 Real Compiler & Runtime Bugs Discovered in Unmodified `intentc`

While building complex multi-collection programs in `gemini-build` (without modifying `intentc`), we uncovered **7 reproducible bugs** in the compiler and runtime—including silent miscompilations where valid English compiles cleanly to the **wrong logical meaning**.

## Where Our Analysis Might Be Wrong & Thoughts for a Reviewing Model (Aligned with Flexibility, Not Rigidity)

We want to explicitly note where our characterization of these 7 behaviors might be incomplete or where a stronger reviewing model may see a deeper, cleaner architectural solution:

1. **Bug 1 (`not between 18 and 30` → `age < 18 and age <= 30`)**:
   - **Why we think it failed**: [`between()`](file:///Users/zen/Desktop/project-10nov/intentc/parser.py#L1108-L1117) runs as a token-stream rewrite *before* [`parse_cond()`](file:///Users/zen/Desktop/project-10nov/intentc/parser.py#L669), turning `between A and B` into `>= A and <= B` without checking whether `NOT` precedes `between`.
   - **Where we might be wrong / how a stronger model might think about it**: If `not between A and B` simply rewrote `and` to `or` (`< A or > B`), what if the user also had another `and` in the same sentence (`whose status is 1 and age is not between 18 and 30`)? Because [`parse_cond()`](file:///Users/zen/Desktop/project-10nov/intentc/parser.py#L688) currently forbids mixing `and` and `or` in one condition, expanding `not between` to `or` would cause `status is 1 and age is not between 18 and 30` to fail with `this condition mixes "and" and "or"`! A stronger model will likely see that `between` (or a negated sub-clause) should be a single node or grouped condition in the IR (`negate(and(ge, le))`), keeping English sentences like `active customers whose age is not between 18 and 30` completely flexible!
2. **Bug 3 (`find-user` with no argument matching `email == ""`)**:
   - **Where we might be wrong**: Perhaps empty strings `""` are intentionally valid text values in Intent (e.g., `add-user ,25` adds a user with an empty email). The subtlety is that `"find-user"` (no space) vs `"find-user "` (one trailing space) cannot be distinguished once `dispatch` sets `%argv` to the NUL byte at the end of `%line` ([`llvm.py:676`](file:///Users/zen/Desktop/project-10nov/intentc/llvm.py#L676)). Passing `null` when `sp == null` (no space after command name) would report `error: missing email` on `"find-user"` while still allowing `"find-user "` to search for `""`.
3. **Bug 4 (Failed mutating commands written to the WAL journal)**:
   - **Where we might be wrong**: Because the language is deterministic, replaying a rejected duplicate (`add-user ,99`) on startup produces the exact same no-op (`duplicate email` with stdout silenced to `/dev/null`). So **state correctness on replay is NOT broken**! The only downside is log bloat and disk writes on invalid inputs, which `@dispatch` could avoid by having task functions return `i32 1` only when a mutation actually occurred.
